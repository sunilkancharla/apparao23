## Controls and acceptance

- Positive startup: staged Python reports expected version/prefix, expected AppContainer SID/zero capabilities, low integrity and Job membership; only standard library and authored helper load. Copy hashes match originals. This does not establish future OCR wheel compatibility.
- File controls: read the allowed synthetic input; create an allowed work output; reject reading/writing the private synthetic sentinel, modifying the read-only input and writing a sibling sentinel directory. Verify actual controller-observed bytes and access-denied errors, not a mocked Python guard. Profile storage is the disclosed exception above.
- Network controls: controller-owned TCP/UDP listeners on numeric IPv4/IPv6 loopback addresses, ephemeral ports, no LAN bind, DNS or external endpoints. An unrestricted positive control must establish that each listener is reachable with a synthetic marker; otherwise that control is inconclusive. AppContainer workers use native Winsock calls with no Python socket monkeypatch. Require explicit access-denied outcomes and no listener-observed marker. Pending TCP (`10035`), timeout, connection refused or accepted UDP send are inconclusive and stop; no retry to obtain a preferable outcome. Verify zero network capabilities and no exemption was added. These controls exercise native loopback denial; they do not empirically test every Internet destination/protocol or assert a complete firewall audit.
- Process/resource controls: verify child creation restriction, one-process Job membership/accounting, a safe timeout sentinel and owned-process teardown. Any unexpected descendant or accounting gap stops the package. No resource bomb or unbounded allocation.
- Passing this preflight permits presenting an OCR-ready boundary proposal, not running OCR. Part B must later revalidate the token/access policy, map only its exact assets/package paths, review additional native needs and receive approval within its own budget. Failure does not authorize switching boundaries or waiving controls.

## Shared budget and stop rules

Proposed **96 total process starts/attempt reservations**, including PowerShell hosts, Python redirectors/interpreters, controller/tests, workers, controls, checks and teardown: 24 helper/test slots, 12 staging/setup, 24 controlled-worker slots, 12 control/teardown, 12 closeout and 12 reserve. Charge before each launch; record actual descendants with Job accounting and conservatively reserve any host/redirector overhead. Reserve is for necessary covered work, not re-running failed controls. Protect cleanup capacity before starting controls; no reset of old ledgers. If the complete controller/descendant meter cannot be established, stop before profile creation.

Limits: **20 minutes preparation and 20 minutes execution** from its first test/controller; one worker at a time, **15 seconds per worker**, **512 MiB private commit per worker/controller**, **>=4 GiB available system RAM**, **256 MiB added disk total** including the staged runtime, profile storage and results, **16 MiB outputs**, **zero downloads/Ollama calls/external requests**. Meter staged/work bytes and profile storage; stop if any cannot be bounded/observed. Controller-owned TCP/UDP controls carry synthetic markers only. All failing tests, controls and regressions count in the same allocation; exclude consumed old parser/model suites. Cleanup/check slots and time must be reserved, not spent on optional extra trials.

Stop on privilege/host restriction, mismatched runtime bytes, unsafe paths, unexpected access/capability/descendant, inconclusive or failed control, insufficient resources, budget exhaustion or incomplete cleanup. Preserve partial evidence. No escalation to an elevated worker, broader ACL, global install or feature enablement is implied. Package approval and host tool escalation remain separate; report a host restriction rather than circumvent it.
