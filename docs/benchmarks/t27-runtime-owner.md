## Implemented ownership and shared work slot

`app/runtime.py` provides `OwnedRuntime(settings, store, home).session()`, a trusted backend async context yielding the existing `Embedder`. It holds the same `UploadStore.busy` slot used by upload/extraction/preview, refuses pending recovery/closed storage and checks asset identities, staged home capacity and port availability before launching. Actual uploads are refused during a session and work again after verified teardown. It assumes the existing single SQLite/event-loop owner, not concurrent cross-thread store mutation.

Only the exact selected server and Nomic assets are verified via existing diagnostics. A private, already provisioned runtime home must be strictly below managed staging; its retained files count as temporary data. The controller neither creates a default user profile elsewhere nor recursively deletes home files. It checks at most 4,096 entries/16,000,000 bytes and requires the existing temporary class to have a further 16,000,000-byte margin before launch. That margin plus the shared work slot is an in-process admission reservation, not a new durable schema or a hard filesystem quota. Unknown scratch survives interruption and remains charged by existing startup accounting. Sampled growth can overshoot between observations; native validation/adoption remains pending.

The child environment is constructed explicitly: pinned model directory, literal loopback authority, project-local profile/config/temp paths, no cloud, one parallel request/model, CPU visibility controls and no inherited proxy/secret/OLLAMA settings. Child PATH is local to this process and contains the selected executable directory and Windows System32; global PATH is unchanged. No app startup service, browser embedding route or readiness transition is introduced.

The owner checks listener/process identity for each client exchange and has an independent 100-ms watcher for deadlines, ownership, resource/TCP state and scratch. A gap above 300 ms stops work. It terminates the owned tree on cancellation, failures or normal context exit; teardown must succeed before releasing the slot. Uncertain teardown keeps `busy` and recovery-pending state, blocking further writes. A blocked-loop control found watchdog errors being swallowed at context exit; the owner now propagates that failure after cleanup.

## Windows native adapter

`app/windows_job.py` defines native layouts and parsing at import without opening a DLL, creating a job or starting a process. Its `WindowsJob` constructor is called only when explicitly entering a session. It sets/readbacks kill-on-close, eight-active-process and job-memory limits. Extended startup `PROC_THREAD_ATTRIBUTE_JOB_LIST` attaches the root **during CreateProcessW**, eliminating a separate create/assign interval. The process is hidden/suspended with handle inheritance disabled; only its owned primary-thread handle is resumed. There is no shell, PID discovery/kill or attachment to an answering service.

Handle-backed liveness and bounded complete membership snapshots must include the exact root. Both IPv4/IPv6 owner-PID tables are parsed; the app port must belong to that root at literal 127.0.0.1. Foreign/wildcard/IPv6 listeners on that port refuse access. Observed external TCP peers of any owned member stop work; unrelated processes are ignored. This is observation, not network confinement. Cumulative job counts include already exited descendants; excess above 16 stops the tree. Memory controls use the worker's private commit, peak job commit and OS physical availability; they do not account for an extra outer test coordinator or establish target-machine acceptance.

Cleanup terminates only the owned job, waits for its root and zero active members, retains cumulative starts and closes owned thread/process/job handles. Failed cleanup retains the handles for a later close attempt and blocks admission. Kill-on-close and non-inherited job handles are intended to terminate descendants if the worker dies; **actual Windows behavior is still untested in this increment**. Filesystem/DLL/model check/use races against a hostile same-account operator are not confined by these controls; the accepted native trust limitations remain.

Implementation references: Microsoft's [job-list startup attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) describes assigning jobs during child creation; [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describes membership/limits/tree termination; [GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable) describes owner-PID endpoint tables. These references support implementation choices, not claims that this adapter has passed native execution.
